# ПР-3. Описание проверок Permission Modes

Документ описывает результаты проверок режимов разрешений (`allow`, `ask`, `deny`) на основе файла `.claude/settings.json` текущего проекта и действий, выполненных в сессии.

## Настройки проекта

Файл `.claude/settings.json` содержит:

- `allow` — 4 правила: `Bash(ls:*)`, `Bash(pwd)`, `Bash(cat:*)`, `Bash(find:*)`.
- `ask` — 1 правило: `Bash(git push:*)`.
- `deny` — 3 правила: `Read(.env)`, `Read(secrets/**)`, `Bash(rm -rf:*)`.

## Проверка allow

Выполнена команда `pwd`. Она запустилась без запроса разрешения и вернула путь к корню проекта. Файлы команда не изменяла. Правило `Bash(pwd)` из `allow` сработало.

Вывод команды:

```text
$ pwd
/Users/diana-dmitrieva/Desktop/GitHub/claude-blog
```

Дополнительно в этой сессии без запроса выполнялись `find` (при проверке структуры проекта для README) — правило `Bash(find:*)`.

## Проверка ask

Выполнена команда `git push --dry-run`. Она подпадает под правило `Bash(git push:*)` из `ask` и требует подтверждения. После разрешения команда выполнилась и вернула `Everything up-to-date`. Настоящей отправки изменений не произошло: флаг `--dry-run` лишь симулирует push, а локальная ветка уже была актуальна относительно удалённой. Файлы и удалённый репозиторий не изменились.

Вывод команды:

```text
$ git push --dry-run
Everything up-to-date
```

## Проверка deny

Попытка прочитать `.env` через инструмент `Read`. Система отклонила доступ. Содержимое файла не запрашивалось и не показывалось. Правило `Read(.env)` из `deny` сработало.

Сообщение системы:

```text
$ Read(.env)
File is in a directory that is denied by your permission settings.
```

Команда `rm -rf` намеренно не выполнялась: она разрушительна и небезопасна для запуска в учебной проверке. Правило `Bash(rm -rf:*)` зафиксировано в `deny`, и при попытке вызова доступ был бы отклонён.

## Проверка обхода запрета через Bash

Правило `Read(.env)` запрещает чтение `.env` инструментом Read, но не закрывает обход через терминал. В `allow` стоит `Bash(cat:*)`, поэтому команда `cat .env` совпадает с разрешённым правилом.

Создан учебный файл `.env` со строкой `TEST=123`. Команда `cat .env` запущена через Bash:

```text
$ cat .env
Permission to use Bash with command cat .env has been denied.
```

Команда заблокирована, несмотря на `Bash(cat:*)` в `allow`. В файлах `.claude/settings.json` и `settings.local.json` правила для `cat .env` нет — значит блокировка пришла не из настроек проекта, а из текущего режима разрешений сессии (дополнительная защита файла `.env` поверх правил файла).

Вывод: файл `.env` защищён двумя слоями. Первый — правило `Read(.env)` в `deny`, оно явно запрещает чтение инструментом Read. Второй — режим сессии, который заблокировал `cat .env` через Bash, даже когда правило `Bash(cat:*)` из `allow` совпадало. Поэтому ограничивать `.env` только через `Read(.env)` недостаточно: запрет на инструмент Read не закрывает обход через `Bash`, и полагаться стоит на режим сессии, а не только на запись в `settings.json`. После проверки учебный файл `.env` удалён.

## Сравнение с /permissions

Правила разрешений проекта заданы в `.claude/settings.json`:

- `allow` — 4 правила.
- `ask` — 1 правило.
- `deny` — 3 правила.

Порядок оценки правил: `deny → ask → allow`. При конфликте `deny` имеет приоритет — даже если команда совпадает с правилом из `allow`, совпадение с `deny` блокирует её выполнение.

## Разница между `Bash(ls *)` и `Bash(ls*)`

- `Bash(ls *)` — пробел после `ls`. Разрешает команды, начинающиеся со строки `ls ` (с пробелом): `ls -la` — да, `ls src/` — да. Не разрешает `lsof`: после `ls` нет пробела.
- `Bash(ls*)` — без пробела. Разрешает всё, что начинается на `ls`: `ls -la` — да, но также `lsof` — да, `lsblk` — да.

Команду `ls -la` разрешают оба правила. Разница в ширине: `Bash(ls*)` случайно захватывает чужие команды (`lsof`, `lsblk`), `Bash(ls *)` — нет. Надёжнее `Bash(ls *)`, а ещё точнее — `Bash(ls:*)` с двоеточием, где двоеточие отделяет команду от её аргументов.
